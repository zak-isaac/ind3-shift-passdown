🛠 Overview

What This Is

A FastAPI web app that runs the shift handoff process for the IND3 Reliability team: technicians log work-order entries during their shift, the MST (lead) reviews them, and at shift end an AI-assisted passdown report gets emailed to the management distribution list.

LayerTechnology
BackendPython 3.13 + FastAPI + Uvicorn
TemplatesJinja2 (server-rendered, no SPA build step)
Live updatesHTMX + a single WebSocket for the MST activity feed
DatabaseSQLite, one file per facility
AILocal Ollama (llama3.1:8b / phi4-mini) — no cloud calls
EmailOutlook COM automation (no SMTP password needed)
🔄 Flow

High-Level Flow

From a technician logging a work order to the passdown email landing in an inbox:

Tech uploads Cetaris Tech types a timecard (CSV/XLSX) manual entry │ │ └───────────┬────────────┘ ▼ entries table (SQLite) │ WebSocket push ──────► MST dashboard (live feed) MST clicks "Generate Report" │ ▼ wo_consolidator.py — group by WO#, then by asset ID │ ▼ ai_rewriter.py — polish each remark via local LLM │ ▼ formatter.py — build HTML preview + email body │ ▼ MST clicks "Compose Email" → .eml file → Outlook → Send │ ▼ MST clicks "End Shift" → locked, moved to History
💡 Consolidation is view-only. Raw technician entries in the database are never merged or overwritten — grouping by Work Order and Asset ID happens fresh every time a report is generated. You can always trace a report line back to the exact entries that produced it.

🧠 AI

The AI Rewrite Pipeline

Everything runs on a local Ollama instance — no cloud LLM calls for this step.

1. Model auto-selection at startup — priority order: phi4:14b → llama3.1:8b → phi4-mini. Whichever's installed and highest in that list wins. Check what's actually running with:

curl http://localhost:11434/api/tags

2. One remark per AI call (not batched) — smaller local models handle a focused single-entry rewrite more reliably than a long batch prompt.

3. Typo-fix pass before the AI ever sees the text — catches known warehouse-specific typos deterministically (e.g. "recalibreted" → "recalibrated").

4. Safety nets on the way out: strip any echoed asset-ID prefix, void vague filler phrases like "assisted with the repair" with no real detail, detect garbage output, and — critically — fall back to the raw (typo-fixed) remark if the AI fails or times out rather than dropping the entry. 90-second timeout per call.

5. Re-grouping after AI happens back in main.py — remarks are grouped by asset ID into nested sub-bullets so an asset touched by multiple Work Orders in one shift renders as one asset heading with a bullet per WO underneath.

✅ If Ollama is down entirely, the report still generates — just without the language polish. Raw remarks pass straight through instead of failing the whole report.
🔒 Security

Auth Model

There are no traditional passwords. Everyone authenticates with their Walmart associate number.

RoleHow they get in
TechAssociate number only, looked up against the roster.
MST / LeadAssociate number acts as a PIN to unlock the MST dashboard. A manager bypass code exists for emergencies.
AdminSame lead-auth check — no separate admin login.
⚠️ Sessions are cookie-based and scoped per shift, so overlapping shifts don't cross-contaminate. Treat associate numbers as sensitive since they double as credentials here.
🚀 Deployment

How It's Hosted

This app is not deployed through AI Launchpad / AI Innovation Lab — it runs as a native Windows Scheduled Task directly on a shop-floor PC.

Task nameIND3PassdownServer
Runs asNT AUTHORITY\SYSTEM — survives logoff, no login required
TriggersSystem boot, hibernate/resume, session connect
Auto-restartEvery 1 minute on crash, up to 99 attempts
Port8765 (firewall rule opened automatically)
Install scriptinstall_service.ps1 — run once, as Administrator
Logsserver.log in the project root

First-Time Install

# Open PowerShell as Administrator, then:
cd "C:\Users\ins0002\Documents\puppy_workspace\IND3-Passdown-Server"
.\install_service.ps1

Health Check

# Is something listening on the port?
Get-NetTCPConnection -LocalPort 8765 -State Listen

# What does the scheduled task think its state is?
Get-ScheduledTask -TaskName IND3PassdownServer | Select-Object TaskName, State

# Tail the last 20 lines of the log
Get-Content ".\server.log" -Tail 20
🔧 Troubleshooting

Common Problems

🚨 "Only one usage of each socket address" / crash-looping every 5 seconds

Something else already owns port 8765 — usually a zombie process from a previous install that was never cleaned up.

Diagnose:

Get-NetTCPConnection -LocalPort 8765 -State Listen
Get-Process -Id <PID> | Select-Object Id, StartTime

If that start time is old and doesn't match your latest install, it's a zombie.

Fix (as Administrator):

Stop-Process -Id <PID> -Force
🔴 Always check for duplicate scheduled tasks after this happens once: 
Get-ScheduledTask | Where-Object {$_.TaskName -like '*IND3*' -or $_.TaskName -like '*Passdown*'}
An old task nobody unregistered will keep spawning zombies forever.

🔄 Code changes don't seem to take effect

The Python process only reads code at startup. Editing files while the service is running does nothing until it restarts. Kill the process (see above) and let the scheduled task's auto-restart pick it back up within ~5-10 seconds.

🧠 AI rewriting isn't happening / reports show raw technician text

Check Ollama is running and has a model:

curl http://localhost:11434/api/tags

If empty, pull one and restart the service:

ollama pull llama3.1:8b

📧 Outlook email won't send

  • Confirm Outlook is installed and set as the default mail client.
  • Confirm an Outlook profile is actively signed in on this machine — COM automation borrows that session.
  • The generated .eml lands in the Downloads folder of whichever Windows account the browser session belongs to.

👤 Adding or removing someone from the roster

Edit the roster Excel file directly, then use the Admin panel's reload button, or restart the service to force a fresh load at startup.

💾 Backing up data

All shift/entry/report history lives in a single file: dbs\ind3.db. Copy it anywhere for a backup — safe to do even while the service is running. No automatic backup job exists today; this is a manual process for now.
